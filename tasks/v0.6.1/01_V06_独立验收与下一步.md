# EA-WM V0.6 独立验收报告与下一步决策
**版本：独立复核 2026-09-22｜依据：本次上传 `v0.6.zip`，不替换为网上仓库**

## 0. 验收结论
**REPAIR_AND_RERUN：先修复实现与评价，再解释模型优劣。**

本轮有实际工程进展：保存 50 Hz 原始轨迹及 20 Hz 派生数据，增加独立 support/query，运行四模型三种子对照，披露 privileged 输入，纠正 V0.5 若干统计与解释错误。
但是，独立检查发现两项会影响核心科学判断的确定性错误：
1. support 的 proprio history 与 command history 分别随机抽样，不保证来自同一交互窗口；
2. residual 经低通/重采样，command 却用保持采样，二者相加被当作真实 execution，所得目标不是已保存的重采样物理 execution。

所以不能接受“本轮无 P0”“跨 episode context 已被证伪”“oracle 无收益证明瓶颈不在 context inference”“M2 已被验证是有效正则”等过强结论。
现有结果不是毫无价值，但主要科学结论要重新检验；不应据此换研究方向，也不应直接扩几千条数据。

## 3. P0-1：support 观测和动作没有成对抽取
源码：`train_sq.py:120–125`。

```python
hp = np.stack([self.by_cond[c][0][rng.integers(0, len(self.by_cond[c][0]))]
               for c in conds])
ha = np.stack([self.by_cond[c][1][rng.integers(0, len(self.by_cond[c][1]))]
               for c in conds])
```

两个 `rng.integers` 独立调用。
实际输入可变成：
- Episode A、时段 i 的速度/IMU/关节历史；
- Episode B、时段 j 的动作历史；
虽然二者属于相同 condition，但并不是同一段动作—响应交互。

这与研究定义 `c=C({u_tau,e_tau,proprio_tau})` 不符。对从自身对齐 history 训练的 M1，换入这种 history 后性能下降，不能直接解释为“同条件跨 episode 迁移不可行”。

独立重放原函数的玩具测试：64 个带同一编号的成对窗口，抽 10,000 次，9,843 次 hp/ha 编号不一致，即 98.43%。**此比率是编号单元测试，不是实际训练抽样比例的测量**；实际 donor ID 没有完整保存。

影响：
- M2 训练及验证；
- M2 测试；
- M1 的 cross_support、diff_condition 对照；
- bootstrap 中相关 variant；
- 从这些结果推导的状态/context 纠缠、正则效果和迁移否定结论。

修复：一次抽取一个窗口 ID，用同一 ID 读取所有模态与 command；记录 support episode、window origin、split 和 donor ID。加入编号对齐单测，而不是只检查维度/条件一致。

## 4. P0-2：派生标签恒等式被破坏
源码：
- `derive_20hz.py:23–24,47–65`
- `train_sq.py:73–85`
- `eval_sq.py:123–130`
- `boot_models.py:67–71`

用 F 表示对连续信号的抗混叠重采样，用 S 表示对 command 的保持采样。当前代码使用：

\[
r^{old}_{20}=F(e-u),\qquad u_{20}=S(u)
\]

再构造：

\[
e^{used}_{20}=u_{20}+r^{old}_{20}
=F(e)+[S(u)-F(u)].
\]

真正已保存在 `lb_execution` 中的目标是 `F(e)`。
因此二者之差为：

\[
e^{used}_{20}-e^{true}_{20}=S(u)-F(u).
\]

这个差异与机器人运动无关，是由 command 的两种不同处理方式造成的，尤其在动作阶跃处突出。

### 4.1 附件中的实际数值
`friction_low_query_Q3_turn_ep_00162.20hz.npz`，t=2.50 s，wz：
- `cmd_vel`：+0.800000
- `lb_residual`：+1.085307
- 评估使用的 `cmd + residual`：**1.885307 rad/s**
- 同文件 `lb_execution`：**0.765099 rad/s**
- 差：**1.120208 rad/s**

12 条代表性派生 episode 全部出现恒等式不成立；原始 50 Hz 数据的 `residual=execution-command` 在复查样本中正确。
将误差再与 `S(u)-F(u)` 对比，最大剩余约 5e-7，支持上述代数解释。

这不是“未来标签被输入模型”式泄漏；它是**物理监督目标构造错误**。
若任务被重新定义为“预测滤波后的 tracking error”，旧标签可以有其含义，但当前报告将 `u+filtered residual` 解释为物理 execution 不成立。不能静默换任务含义保留主结论。

### 4.2 修复原则
保留原始数据，不原地覆盖：
1. 先按明确时间语义构造物理 execution 目标 `e_label`；
2. 构造对齐的、按事件语义采样的 `u_ref`；
3. **最后**计算 `r_label=e_label-u_ref`；
4. 所有评估以保存的 `e_label` 为独立真值，不能只用 `u+r` 自证；
5. 若模型输出 residual，`u_ref+r_hat` 必须对比 `e_label`；
6. 每条 episode、每个 axis 做 `assert_allclose(u_ref+r_label,e_label)`。
7. 若 labels 采用离线非因果抗混叠，明确这是平滑物理目标；输入仍必须因果。滤波边界与相位另记，不能混淆瞬时真值。

证据：`label_identity_audit.csv`、`label_identity_examples.csv`。

## 5. P1-1：浮点累计时间让 command 边界晚取一帧
50 Hz 原始 timestamp 由 `t_abs += 0.02` 累加；20 Hz 使用理论 grid。
`searchsorted(t,grid,side="right")-1` 在理论相同时间遇到浮点尾差，会选择上一个采样。

实例：
- 原始 125 号控制 tick 的时间约 2.5000000000000018；
- 查询 grid 是 2.5；
- 当前代码取 index 124，command 仍 +0.8；
- 按声明的控制 tick 语义，125 号 tick 的 command 已是 -0.8。

在 4 s 的代表性 query 中，80 个 grid 点有 36 个与整数 tick 对齐的保持索引不同；Q3 中有 3 个 command 值受影响。不是 36 个都有 command 变化。
修复：统一整数物理/控制 tick；用有理数网格处理 50→20 Hz。不要为了碰巧通过某个样本随意增大 epsilon。真实传感器时间不等间隔时，保留实际时间和样本年龄，不伪造精确观测时刻。

另需运行时审计 `run_wave`：
先写 cmd，却把上次 `env.step` 返回的 `obs` 直接送给 `policy(obs)`。当前快照没有显示 observation 在写 cmd 后重建。可能存在“日志命令”与“policy 实际看到的命令”差一控制步的问题。
**这是源码风险，尚未在安装环境实测确认。** 要记录 policy 输入中 command 切片，不能仅靠 command/execution 相关系数确认。

证据：`timegrid_audit.csv`、`command_event_grid_examples.csv`。

## 6. P1-2：persistence 把 v_z 当成了 wz
输入字段依次为：
- 0:3 = base linear velocity [vx,vy,vz]
- 3:6 = angular velocity [wx,wy,wz]
- 后续为 gravity/IMU/joint/contact。

`eval_sq.py:129` 用 `hp[:,-1,:3]` 当作 [vx,vy,wz]。第三项实际是垂向线速度。
`k0_continuity` 同样使用该错误切片。

应由显式 schema 抽取 [0,1,5]，不能依赖散落的魔法索引。
修复不保证 persistence 一定更好：24 个导出的 normal 示例中，正确 wz persistence 的旧标签 MAE 反而更高。但这正说明**需要正确比较，不是选择对自己有利的错误基线**。
“首步连续性破坏”须按正确轴、预测第一步真实间隔及原生响应来评价，不能使用旧 k0 数字作机制结论。

## 7. P1-3：held-anchor 测试与报告不一致
报告声称 held-anchor 为 AQ6/AQ7 的 Q1–Q3。
代码 `roles["test"]` 同时包含全部 Q4；筛选 AQ6/7 后没有排除 Q4。

1. unseen_anchor_seen_family：AQ6/7，Q1–Q3；
2. seen_anchor_unseen_family：AQ0–4，Q4；
3. unseen_anchor_unseen_family：AQ6/7，Q4。

## 8. P1-4：fixed lead 实际是 prefix average；主口径发生变化
`mae_rows`：
```python
err[:, :k, i].mean()
```
这是从第一未来步到 k 的平均，不是第 k 步单点。
正确区分：
\[
MAE_{lead}(h)=E|\hat e_{t+h}-e_{t+h}|
\]
\[
MAE_{prefix}(h)=\frac1h\sum_{j=1}^{h}E|\hat e_{t+j}-e_{t+j}|.
\]
分别保存；主表按预注册固定 lead 每轴报告。
旧 `MAE_all` 还将 m/s 和 rad/s 直接平均，可作历史兼容描述，不能无说明替代预注册主指标。
`per_axis_and_pose_metrics.csv` 未包含相对位姿指标，仅是旧 A 阶段速度指标；代码包不足以支持“已经验证净姿态/位姿排序一致”。

## 9. 统计、oracle 和重复实验的结论应怎样收紧
### 9.1 统计
A 阶段旧 pair 的 two-way 处理是进步，但 C 阶段 `boot_models.py` 使用 episode ID 为 cluster，未按 query anchor/support donor 的交叉依赖重采样。
同一 AQ 的条件、rep 和 family 有共享信息；两个测试 AQ 不等于 48 个独立 anchor。
three training seeds 不能替代独立环境组。当前统计应标描述性/探索性，而非“所有显著、因素已经排除”。

### 9.2 Oracle
M3 是在 learned c 上加一个零初始化 `Linear(1,8)` 的真实 friction 映射。
这个实现的无增益最多说明：**该条件注入方式在当前训练和错误目标上没有明显改善**。
不能证明真实工况信息无用，也不能证明扩大独立数据无效，更不能定位唯一瓶颈为不可约噪声。
修复后先验证摩擦确实影响正确物理目标、oracle 分支输出是否响应输入，再谈上下文估计瓶颈。Oracle 是诊断基线，不保证上界。

### 9.3 条件重复
rep=1 通过 `jittered()` 改变命令段长度；rep0/rep1 并非同一 (state, future command) 的两次随机结果。
不能直接用这两条轨迹差异估计 `Var(E | state, U)` 或“不可约误差”。
需要完整相同条件、明确随机源的重复，或在充分的匹配条件下分析。两次重复本身也不够确定噪声下界。

### 9.4 摩擦
机器人 static/dynamic material 写入读回已记录，这是进步；但 average combine 是代码常量，不是引擎枚举读回。
如果确为 average 且 ground static=dynamic=1：
- static 有效值为 1.0/0.8/0.65；
- dynamic 有效值为 0.85/0.71/0.605；
两者不能混成一个“真实摩擦”。在核验前只用 written_static/written_dynamic 档位命名。

## 10. 哪些结论可以保留？
保留：
- 240 条 pilot 的采集流程、50 Hz 原始日志和 readback 等工程产物；
- 对旧 V0.5 部分数值的复算与解释纠正；
- 旧实现的具体误差表可以重现；
- 新的可控 support/query 框架值得继续验证。

暂缓：
- M2 是有效跨支持正则；
- context 不是可迁移物理编码；
- M1/M2 真实物理预测显著优于 Direct/ARX；
- 工况识别不是瓶颈；
- 已定位不可约噪声、无需扩大数据；
- 部署成功或需要立刻改变论文方向。

## 12. 与 CVPR 主线的关系
当前尚处于 execution dynamics pilot，没有完成 JEPA 视觉世界模型或闭环纠正验证。
修复不要求更换 `Command → Execution → Future → Correction` 主线；只需恢复每一步输入/监督的物理含义。
可以并行准备少量 RGB 同步、真实机器狗传感器接口和冻结 V-JEPA 编码器加载；不要将大规模视觉训练作为修复当前 P0 的替代。
实际部署的观察量（IMU、关节、接触估计、odom）需与仿真 privileged GT 分开建表。
